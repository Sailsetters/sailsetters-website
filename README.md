# Sailsetters Website

Website des Sailsetters e.V. — [sailsetters.de](https://sailsetters.de)

## Stack

- **Next.js 16** (App Router) — deployed on Vercel
- **React 19**
- **Tailwind CSS 4** — configured CSS-first in `app/(frontend)/globals.css`, no `tailwind.config.ts`
- **TypeScript 6**
- **Payload CMS 3** — admin panel, application and contact forms, on Postgres

The site is **German only**. There is no internationalisation and none is planned.
The admin panel is set to German as well.

## Entwicklung

Requires Node.js 20.19+, 22.13+, or 24+, and Docker for the local database.

```bash
# 1. Start a local Postgres (port 5433 to avoid clashing with other projects)
docker run -d --name sailsetters-postgres \
  -e POSTGRES_USER=sailsetters \
  -e POSTGRES_PASSWORD=sailsetters_dev \
  -e POSTGRES_DB=sailsetters \
  -p 5433:5432 postgres:17-alpine

# 2. Environment
cp .env.example .env.local        # then set PAYLOAD_SECRET

# 3. Run
npm install
npm run dev                        # http://localhost:3000
```

On first run open `/admin` and create the first user.

Other scripts:

```bash
npm run build               # production build (also type-checks)
npm run lint                # eslint
npm run typecheck           # tsc --noEmit
npm run generate:types      # regenerate payload-types.ts after schema changes
npm run generate:importmap  # regenerate the admin import map
npm run seed                # fill an empty database with the homepage content
```

`payload-types.ts` and `app/(payload)/admin/importMap.js` are generated but
**committed**. Note that `npm run build` needs a reachable database since the
homepage is rendered from Payload at build time.

## Struktur

```
app/
  (frontend)/     the public website
    page.tsx        homepage
    impressum/      Impressum (§ 5 TMG)
    satzung/        Vereinssatzung
    globals.css     Tailwind entry + brand tokens and base type
    fonts.ts        Fraunces + Inter via next/font
  (payload)/      admin panel and API, generated by Payload — do not edit
collections/    Payload data model
components/     shared frontend components
public/         logo, blobs, partner logos, Satzung PDF
docs/           design guide
```

Both `(frontend)` and `(payload)` are route groups, so they do **not** appear in
URLs. The split exists because each group needs to own its own `<html>` element.

### Seiten aus Payload

Die Startseite (aktuelle Projekte, Havens & Partner, Kennzahlen), `/projekte`
(aktuelle und vergangene Projekte) und `/verein` (Vorstand) werden statisch
aus Payload gerendert. Jede Änderung an diesen Collections ruft
`revalidatePath` für die drei Seiten auf (siehe `lib/revalidate.ts`), sodass
sie sofort sichtbar ist, ohne dass jemand deployen muss.

Die Startseite zeigt alle aktuellen Projekte. Abgeschlossene Projekte werden
auf „Vergangen“ gesetzt, nicht gelöscht: Sie verschwinden dann von der
Startseite und erscheinen unter „Vergangene Projekte“ auf `/projekte`.

`npm run seed` befüllt eine leere Datenbank mit dem Stand der alten Website
(Logos aus `scripts/seed-assets/`). Der Befehl überspringt Collections, die
schon Inhalte haben, und ist beim ersten Produktivgang einmal gegen die
Produktionsdatenbank auszuführen.

### Bewerbungsprozess

Der `status` einer Bewerbung ist die Pipeline:
`neu → in-pruefung → eingeladen → gespraech-geplant → angenommen → onboarding → mitglied`,
mit `abgelehnt` und `zurueckgezogen` als Ausstiege.

Zwei Übergänge legen automatisch einen E-Mail-Entwurf aus der jeweiligen
Vorlage an: **Eingeladen** (Einladung mit Meeting-Link) und **Angenommen**
(Zusage mit Slack-Link). `{{name}}` und `{{bearbeiter}}` werden dabei
eingesetzt; alle anderen Platzhalter — etwa `{{meetingLink}}` — bleiben stehen
und müssen von der bearbeitenden Person ersetzt werden. Der Entwurf erscheint
unten auf der Bewerbung, wird dort geöffnet, geprüft und mit Status
„Jetzt senden“ gespeichert. Gesendete E-Mails sind eingefroren und dienen als
Nachweis, was der Person mitgeteilt wurde.

Notizen zu einer Bewerbung sind nur intern sichtbar und werden beim Speichern
automatisch mit Autor:in und Zeitpunkt versehen.

Das Formular ist nur in den Bewerbungsfenstern offen: 1. bis 21. Oktober und
1. bis 21. April (Berliner Zeit, siehe `lib/bewerbungsphase.ts`). Das Global
„Bewerbungsphase“ kann es unabhängig davon öffnen oder schließen; das gilt
auch serverseitig, ein direkter Post an das Formular wird dann abgelehnt.

Applicant and contact data is personal data under the DSGVO. Both form
collections require an explicit `consent` checkbox, and neither is readable
without a login. Uploaded CVs (`application-files`) are never public: locally
they live in `uploads/` outside `public/` and are served through the API with
login only; in production they are stored as *private* Vercel blobs via
`lib/privateBlobAdapter.ts` (the official plugin only supports public blobs).
Deleting an application deletes its emails and its CV.

### Design

The brand is documented in `docs/Sailsetters_Design_Guide.md` (colours,
type, logo and blob usage, plus the PowerPoint template). The website
follows it:

- **Colours** live in the `@theme` block in `app/(frontend)/globals.css` and
  are available as normal Tailwind utilities (`bg-sand`, `text-ink`, …).
  Sunrise and Coral are surface colours only — they fail WCAG contrast as text
  on Sand. Text is Ink, Driftwood, Port or Harbour.
- **Type** is Fraunces (headings, weight 600 — never bolder) and Inter (body),
  both loaded as variable fonts through `next/font/google` in
  `app/(frontend)/fonts.ts`. `h1`–`h4` pick up Fraunces from the base layer,
  so headings need no font class.
- **Assets** in `public/`: the logo mark as `logo_ink`, `logo_paper`,
  `logo_port`, and five gradient blobs (`blob_*`) meant for backgrounds at
  low opacity — at most one at full opacity per view.

| Token       | Hex       | Use                                   |
| ----------- | --------- | ------------------------------------- |
| `sand`      | `#f7f1e7` | page background                       |
| `dune`      | `#ede3d3` | quiet sections, table heads           |
| `paper`     | `#ffffff` | cards on Sand, inputs                 |
| `ink`       | `#1f1a17` | headings and body text                |
| `driftwood` | `#6a5f57` | captions, secondary text              |
| `sunrise`   | `#ee6c3e` | blobs, icons, gradient start          |
| `coral`     | `#d9527a` | second accent, gradient end           |
| `port`      | `#8c2f39` | buttons, key figures, links on hover  |
| `harbour`   | `#21414f` | charts, dark sections                 |
| `tide`      | `#5c8a8c` | second data series                    |

## Vor dem Produktivgang

Still open before this can serve real traffic:

- **Hosting**: Vercel Pro (the Hobby plan is not covered by Vercel's DPA).
- **Database**: point `DATABASE_URI` at the Neon (Frankfurt) instance. Use the
  **pooled** connection string (host contains `-pooler`) — serverless functions
  exhaust an unpooled one. Neon's Vercel integration injects `DATABASE_URL`
  instead of `DATABASE_URI`; the config accepts either.
- **Schema**: Payload only pushes the schema automatically when
  `NODE_ENV !== 'production'`, so a fresh production database starts empty and
  the build fails. Either generate migrations (`payload migrate:create`, then
  `payload migrate`) or, for a test deployment, point `.env.local` at the new
  database and run `npm run dev` once to create the tables, then `npm run seed`.
- **Media storage**: two Vercel Blob stores in `fra1`, since a store is public
  or private for its whole lifetime: a public one for `media` (partner logos,
  board photos) as `BLOB_READ_WRITE_TOKEN`, and a private one for
  `application-files` (CVs) as `PRIVATE_BLOB_READ_WRITE_TOKEN` (or
  `PRIVATE_READ_WRITE_TOKEN`, the name Vercel generates for a second store
  connected with the prefix `PRIVATE`). Setting the
  first without the second fails the build on purpose, so CVs never land on
  Vercel's ephemeral filesystem. Then `npm run seed` once against the
  production database.
- **Email**: set the `SMTP_*` variables to the IONOS mailbox that should send
  (see `.env.example`). Without them nothing is sent — drafts can still be
  written, but „Jetzt senden“ only logs to the console.
- **Migrations**: the schema is currently pushed automatically in dev. Generate
  real migrations (`payload migrate:create`) before deploying.
- **Datenschutzerklärung**: legally required once the forms collect data.
